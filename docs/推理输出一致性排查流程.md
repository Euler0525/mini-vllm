# 推理输出一致性排查流程.mdHF、mini_llm 与 vLLM 输出一致性排查流程

本文整理三个推理后端的输出一致性排查方法，并收录本次 13 条分歧的完整根因验证、逐条结果与复现命令。配合 [基线验证与性能评测手册](vLLM基线验证与性能评测手册.md)、[run_inference.py](../benchmarks/inference/run_inference.py) 和 [compare_outputs.py](../benchmarks/inference/compare_outputs.py) 使用。先固定任务、定位首个分歧，再用相同上下文复查候选；不要先修改权重或强行提高误差容限。

## 实验条件与结果口径

原始输入保存在 `artifacts/inference/inputs/prompts.jsonl`，三个后端的结果保存在 `artifacts/inference/results/{hf,mini,vllm}-fixed16.json`。排查时保留原始文件，探针使用独立输入和新的结果文件名。

| 检查项 | 核对内容 |
| --- | --- |
| 模型 | 模型名称、实际 snapshot 路径与 revision；怀疑本地文件被修改时，再核对权重文件哈希 |
| 精度 | 权重与计算 dtype、KV cache dtype、是否使用量化 |
| 输入 | `inputs_sha256`、请求的 `(id, repeat)`、逐条 `prompt_token_ids`；只比较可见文本不足以确认任务相同 |
| 输出预算 | `max_new_tokens`、`max_model_len`、实际输出 token 数 |
| 停止行为 | `ignore_eos`、`eos_token_id`，以及是否额外设置 stop token 或 stop string |
| 采样 | greedy、temperature、top-p、top-k、repetition/frequency/presence penalty、seed、是否使用模型自带 generation config |
| 执行环境 | `environment` 中的版本、源码 commit、GPU，以及日志中的 attention backend、runner、graph/compile 状态 |

先在仓库根目录运行比较，确认脚本没有报告配置、输入或请求集合不一致：

```bash
cd ~/Desktop/mini-vllm
.venv/bin/python benchmarks/inference/compare_outputs.py \
  hf-fixed16.json mini-fixed16.json vllm-fixed16.json
```

比较脚本会核对已记录的公共配置、请求集合和 prompt IDs；实际 kernel、额外停止条件和未记录的采样选项仍需结合执行脚本、命令与启动日志核对。`differences` 非空时脚本也会正常输出，这表示完成了比较，不表示输出一致。

`identical` 是整条生成 token 序列完全相同的请求数。`first_difference_index` 从零计数：值为 `3` 表示前 3 个生成 token 相同，第 4 个开始不同。`reference_token` 和 `candidate_token` 是该位置的 token ID；若一侧序列先结束，对应值可能是 `null`。完整序列一致率不能当作模型回答准确率或逐 token 一致率。

## 按顺序定位分歧

1. **先确认是同一任务。** 按上表核对 snapshot、dtype、prompt IDs、输出预算、EOS 与采样。输入 token 不同、输出预算不同或一侧提前停止时，先解决实验条件差异，再讨论数值路径。
2. **首 token 不同时查看 `first_top5`。** 同时记录实际选中的 `token_ids[0]`、候选 token、归一化 logprob，以及同一后端 top-1 与 top-2 的间距。候选接近或并列可以解释为什么 greedy 对数值变化敏感，但不能单凭间距小就判定实现正确。不要把这些 logprob 当作原始 logits；并列时 top-k 列表的首项也不一定是实际选中的 token。
3. **后续 token 不同时只分析共同前缀下的首个分歧。** 设报告中的零基下标为 `k`，先验证两边的 `token_ids[:k]` 相同。索引 `k` 对应第 `k+1` 个生成 token；索引 `k+1` 及以后的条件输入已经不同，不能继续把两条自由生成序列逐位置对比为同一上下文上的数值误差。原始结果的 `first_top5` 只记录首个生成位置，不能用它解释 `k > 0` 的分歧。
4. **用相同上下文创建单步探针。** 将原始 prompt IDs 追加 HF 的前 `k` 个生成 IDs，即 `prompt_token_ids + hf_token_ids[:k]`，让三个后端各生成一个 token，并记录 `first_top5`。`k=0` 时不追加生成 token。保持其余实验条件不变，探针单独存储。
5. **根据证据选择后续路径。** HF 与 mini 不一致时，先检查已有的 [权重测试](../tests/test_weights.py)、[RoPE 测试](../tests/test_rotary_embedding.py)、[KV cache 测试](../tests/test_kv_cache.py) 和 [模型对照测试](../tests/test_qwen2p5_model.py)，必要时比较 cached decode 与完整前向、逐层中间张量。vLLM 差异则登记实际 attention backend、版本与融合路径，结合 [执行链与性能分析手册](vLLM执行链追踪与性能分析手册.md) 继续定位。一次历史 RoPE 故障的完整证据见 [本地模型生成结果不一致排查](本地模型生成结果不一致排查.md)，不能直接套用为本次根因。

固定长度实验中的 `ignore_eos=true` 会使生成越过 EOS。记录首个 EOS 的位置，并区分分歧发生在 EOS 之前、EOS 处还是之后；正常 EOS 停止行为需要另开实验验证。

## 创建与运行单步探针

### 创建探针输入

以下命令自动选择第一条 HF/vLLM token 差异，以 `(id, repeat)` 对齐请求，并拒绝覆盖已有 `probe.jsonl`。没有差异时只打印说明。执行前应已通过上一节的公共配置检查。

```bash
cd ~/Desktop/mini-vllm
.venv/bin/python - <<'PY'
import json
from pathlib import Path

root = Path("artifacts/inference")
hf = json.loads((root / "results/hf-fixed16.json").read_text())["requests"]
vl = json.loads((root / "results/vllm-fixed16.json").read_text())["requests"]
gold = {(r["id"], r["repeat"]): r for r in hf}
other = {(r["id"], r["repeat"]): r for r in vl}
assert len(gold) == len(hf) and len(other) == len(vl), "Duplicate requests"
assert gold.keys() == other.keys(), "Missing or extra requests"
assert all(a["prompt_token_ids"] == other[key]["prompt_token_ids"]
           for key, a in gold.items()), "Prompt token IDs differ"

for key, a in gold.items():
    b = other[key]
    k = next((i for i, (x, y) in enumerate(zip(a["token_ids"], b["token_ids"]))
              if x != y), None)
    if k is None:
        if len(a["token_ids"]) != len(b["token_ids"]):
            print("Only output length differs:", key, "; inspect stopping first.")
            break
        continue
    assert a["token_ids"][:k] == b["token_ids"][:k]
    probe = {
        "id": f"{a['id']}-r{a['repeat']}-probe",
        "prompt_token_ids": a["prompt_token_ids"] + a["token_ids"][:k],
    }
    path = root / "inputs/probe.jsonl"
    with path.open("x", encoding="utf-8") as file:
        file.write(json.dumps(probe, ensure_ascii=False) + "\n")
    print("Probe created:", probe["id"], "divergence index:", k)
    print("Prompt tokens:", len(probe["prompt_token_ids"]), "path:", path)
    break
else:
    print("No HF/vLLM token mismatch; skip the probe.")
PY
```

本次结果中第一条差异为 `p01`，`repeat=0`、`k=3`，因此探针使用原始 prompt 加 HF 的前 3 个生成 token，共同生成前缀解码为 `A key-value`。不要追加索引 `3` 处已经不同的 token。

### 分别运行三个后端

仅在生成了探针时运行下面的命令。输入相对于 `artifacts/inference/inputs/`，输出相对于 `artifacts/inference/results/`；这由 `run_inference.py` 处理。结果文件拒绝覆盖，重跑时为三个后端统一换用新的一组文件名。vLLM 解释器路径按本机实际目录调整，保留其独立环境。

```bash
cd ~/Desktop/mini-vllm
set -euo pipefail
mkdir -p artifacts/inference/logs

.venv/bin/python benchmarks/inference/run_inference.py \
  --backend hf --inputs probe.jsonl --output hf-probe1.json \
  --max-new-tokens 1 --max-model-len 2048 --ignore-eos --logprobs \
  2>&1 | tee artifacts/inference/logs/hf-probe1.txt

.venv/bin/python benchmarks/inference/run_inference.py \
  --backend mini --inputs probe.jsonl --output mini-probe1.json \
  --max-new-tokens 1 --max-model-len 2048 --ignore-eos --logprobs \
  2>&1 | tee artifacts/inference/logs/mini-probe1.txt

~/Desktop/vllm/.venv/bin/python benchmarks/inference/run_inference.py \
  --backend vllm --inputs probe.jsonl --output vllm-probe1.json \
  --max-new-tokens 1 --max-model-len 2048 --ignore-eos --logprobs \
  2>&1 | tee artifacts/inference/logs/vllm-probe1.txt

.venv/bin/python benchmarks/inference/compare_outputs.py \
  hf-probe1.json mini-probe1.json vllm-probe1.json
```

### 读取候选并判断下一步

下面只读取探针结果并用本地 tokenizer 解码，不加载模型权重：

```bash
cd ~/Desktop/mini-vllm
.venv/bin/python - <<'PY'
import json
from pathlib import Path
from transformers import AutoTokenizer

root = Path("artifacts/inference/results")
tok = AutoTokenizer.from_pretrained(
    "artifacts/models/qwen2.5-0.5b", local_files_only=True
)
for name in ("hf", "mini", "vllm"):
    doc = json.loads((root / f"{name}-probe1.json").read_text())
    assert len(doc["requests"]) == 1
    row = doc["requests"][0]
    top = sorted(row["first_top5"], key=lambda item: item["logprob"], reverse=True)
    print("\nBackend:", name, "request:", row["id"])
    print("Selected:", row["token_ids"], repr(tok.decode(row["token_ids"])))
    for item in top:
        token = item["token_id"]
        print(token, repr(tok.decode([token])), "logprob:", item["logprob"])
    if len(top) >= 2:
        print("Top-1 minus top-2:", top[0]["logprob"] - top[1]["logprob"])
PY
```

先看 HF/mini 是否仍一致，再看 HF/vLLM 是否复现分歧，以及竞争候选是否相同、是否接近并列。不设置未经验证的统一间距阈值；记录实际数值、执行条件和可推翻当前解释的后续实验。

单步探针保证三个后端接收相同的 token 上下文，但会把原先分步 decode 的前缀改为一次 prefill，因此不保证重现原始 decode 的数值路径。若探针中分歧消失，只能记录为“同上下文 prefill 探针未复现”；仍需在原始生成过程中记录第 `k` 步的候选，或通过强制输入共同 token 前缀保留 cached decode 路径继续验证。

探针文件不能混入原来的 20 条正确性结果，也不能作为正常 EOS 行为或正式性能测试的替代。

## 本次 13 条分歧的完整验证

2026-10-20 已完成本次全部 13 条分歧的验证。根因是 BF16 下 RMSNorm、RoPE、合并投影 GEMM 和 attention 的计算与舍入路径不同，改变了候选排名；greedy 再将第一次选择差异传播到后续生成。将这四类路径在 vLLM 进程内替换为参考实现后，13 个分歧位置的全词表 logits 均与 HF 逐元素一致，13 条完整序列的 208 个生成 token 也全部一致。

模型、输入、采样配置和分页 KV 内容均有实际核验；PyTorch/Transformers 版本差异在本输入集合上未单独导致分歧。所有替换仅用于诊断进程，没有改动权重文件或生产推理实现，也没有放宽数值误差容限。原始 `comparison.json` 及三个 `*-fixed16.json` 保持不变。

| 检查 | 实测结果 | 支持的结论 |
| --- | --- | --- |

| 加载后权重 | HF/mini 各核对 290 个参数张量，vLLM 核对 170 个；均与 snapshot 逐元素一致 | 没有发现加载或权重映射错误；vLLM 张量较少是因为 QKV 和 gate/up 打包 |
| 原始路径重放 | HF、mini、vLLM 均逐条复现各自原始 13 条完整序列 | 分歧可稳定复现，采集没有改变原始结果 |
| 版本环境对照 | 在 vLLM 环境运行 HF eager，13/13 条序列、208/208 个 token、13 个目标位置的全词表 logits 均与原 HF 环境一致 | 不能直接归因于 PyTorch/Transformers 版本号 |

单步 prefill 探针只在 8/13 条上保留 HF/vLLM 差异，另 5 条在该实验中相同；其中 `p05` 的 HF 选择本身也从 `G` 变为 `Graph`。正式归因因此使用原始逐步 decode 重放，以及强制输入 HF 共同前缀的实验。强制操作只决定前缀位置送入下一步的 token；候选分数取自强制处理之前，目标分歧位置不进行强制选择。

### 已定位的数值路径

#### 首个张量分歧出现在 RMSNorm

在全部 13 条请求的目标位置，Embedding 输出和第 0 层 RMSNorm 输入完全一致，但该 RMSNorm 的输出已经不同。HF 在乘 learned weight 前将归一化结果舍入到 BF16，vLLM CUDA kernel 则在 FP32 中完成归一化与权重相乘后再舍入。

设 `u` 是 FP32 归一化结果、`w` 是同一份 BF16 权重，两条路径分别近似为 `bf16(bf16(u) * w)` 和 `bf16(u * w)`。在 GPU 上逐元素重算，双次舍入公式复现了全部 13 条的 HF 首层 RMSNorm 输出。单次舍入公式复现了 11 条的全部元素，另两条各剩 1 个元素差异；简化公式未覆盖 CUDA 归约与 `rsqrt` 的全部实现细节，不能当作 CUDA kernel 的逐位模拟。

例如 `p19` 首层 RMSNorm 的 34,944 个元素中，HF/vLLM 有 9,103 个不同，最大绝对差 `0.015625`。完整参考路径对照在全部 13 个目标位置实现全词表 logits 精确一致，没有依赖容差。逐元素计数见最终审计结果的 `first_rms_norm`。

#### 其余路径的独立对照

| 路径 | 对照方式 | 已确认的差别 |
| --- | --- | --- |
| RMSNorm | 显式 PyTorch RMSNorm，权重与 epsilon 不变 | 归约、乘权重和 BF16 中间舍入位置不同 |
| RoPE | 使用同一 vLLM cos/sin cache，改用 native 旋转 | CUDA 在 FP32 中计算旋转后转换；参考路径保留 BF16 乘法的中间舍入，不是历史 `inv_freq` dtype 故障 |
| QKV、gate/up 投影 | 拆分已核验的打包权重，独立 `F.linear` 后拼接 | 合并 GEMM 的形状和累加路径不同；没有修改权重数值 |
| attention | 显式 QK、causal mask、FP32 softmax 转 BF16、与 V 相乘 | FlashAttention 与 eager 的中间精度、归约和物化路径不同；分页 KV 已独立核对 |

`enforce_eager=True` 关闭编译和 CUDA Graph，并不会将这些 CUDA 算子变成 HF 的 eager 计算步骤。第一处 RMSNorm 差异也不意味着后续分歧只能归因于 RMSNorm；各路径经过多层传播，共同影响最终排名。

#### 干预结果

下表均在相同 prompt 与相同 HF 生成前缀下比较 13 个目标位置，替换仅作用于当前进程内的诊断模型。

| 相对原始 vLLM 的干预 | 恢复 HF token 的位置数 |
| --- | ---: |
| 不替换，强制相同共同前缀 | 0/13 |
| 只替换 RMSNorm | 5/13 |
| 只替换 RoPE | 4/13 |
| 只拆分合并 GEMM | 5/13 |
| 只替换 attention | 6/13 |
| 只替换 SiLU 激活 | 0/13 |
| 同时替换 RMSNorm、RoPE、合并 GEMM、attention | **13/13；全词表 logits 也全部逐元素一致** |

再从完整参考路径中逐项保留原优化实现，核验它们的实际影响：

| 保留原始 vLLM 的部分，其余用参考实现 | HF token 仍一致 | 全词表 logits 完全一致 |
| --- | ---: | ---: |
| RMSNorm | 6/13 | 0/13 |
| RoPE | 8/13 | 0/13 |
| 合并 GEMM | 8/13 | 0/13 |
| attention | 3/13 | 0/13 |
| SiLU 激活 | **13/13** | **13/13** |

因此 SiLU 不是本次消除分歧所需替换的因素。保留原始 SiLU，仅统一其余四类路径，再自由生成完整 16 token，13/13 条序列和 208/208 个 token 仍与 HF 一致；后续生成没有依赖强制前缀。

### 逐条结论

`k` 为零基生成下标。定义原始分歧的 HF token 为 `H`、vLLM token 为 `V`，`Δ = logit(H) - logit(V)`；正值偏向 H，负值偏向 V。这里的原始 logits 是本次从模型采集的，并非原有 `first_top5` 中的归一化 logprob。

| 请求 | k | HF token | vLLM token | HF Δ | vLLM Δ | 单项干预可恢复 HF 的路径 |
| --- | ---: | --- | --- | ---: | ---: | --- |
| p01 | 3 | `store` | `cache` | 0.125 | -0.25 | attention |

### 复现与适用范围

先按 [基线手册](vLLM基线验证与性能评测手册.md) 生成三份原始 `*-fixed16.json`。下列命令使用新的诊断目录，已有结果拒绝覆盖，重跑统一更换目录名。工具自动保存模型文件和原始结果的哈希清单。命令依次运行，同一时间只有一个后端占用 GPU。

```bash
cd ~/Desktop/mini-vllm
set -euo pipefail
for backend in hf mini; do
  .venv/bin/python benchmarks/inference/trace_divergence.py \
    --backend "$backend" --mode replay \

~/Desktop/vllm/.venv/bin/python benchmarks/inference/trace_divergence.py \
  --backend hf --mode replay \
  --output-dir artifacts/inference/diagnostics/root-cause-reproduce/torch214

~/Desktop/vllm/.venv/bin/python benchmarks/inference/trace_divergence.py \
  --backend vllm --mode replay \
  --variants baseline all kv-audit norm+rope+split+attention \
  --output-dir artifacts/inference/diagnostics/root-cause-reproduce

~/Desktop/vllm/.venv/bin/python benchmarks/inference/trace_divergence.py \
  --backend vllm --mode forced \
  --variants baseline norm rope activation split attention all \
    rope+activation+split+attention norm+activation+split+attention \
    norm+rope+split+attention norm+rope+activation+attention norm+rope+activation+split \
  --output-dir artifacts/inference/diagnostics/root-cause-reproduce

.venv/bin/python benchmarks/inference/audit_divergence.py \
  --root artifacts/inference/diagnostics/root-cause-reproduce --device cuda
```

工具依赖当前固定 Qwen snapshot、模型维度和单次固定 16-token 实验。vLLM worker 通过扩展类与具名 RPC 接收普通数据参数，无需启用 pickle 序列化回退。日志中的 runner、attention backend 和算子路径要随版本重新核对；参考算子替换属于诊断，不作为性能优化提交。

本次完成的是这 13 条分歧到算子数值路径层级的根因验证，不代表全部模型、输入、长度或 GPU 均要求逐 token 一致。后续使用原优化路径做性能测试时保留这些差异和证据，不必为了该小集合的完全一致而关闭优化。

## 排查记录模板与完成标准

每轮实验按下面的模板记录，原始结果、探针结果与性能测试分别保存。本次完整结论、逐条记录和复现命令统一保留在本文，原始日志与张量证据保留在 `artifacts/`。

| 记录项 | 应填写的内容 |
| --- | --- |
| 实验与来源 | 日期、源码 commit、完整命令、输入和输出路径、输入哈希 |
| 公共条件 | snapshot、dtype、prompt IDs、输出预算、EOS、采样是否已核对 |
| 环境变量 | 后端版本、GPU、attention backend、runner、融合路径、compile/graph 状态；未确认项明确写出 |
| 分歧位置 | `(id, repeat)`、零基下标 `k`、共同前缀 token IDs、两侧候选 ID 和解码文本 |
| 候选证据 | 各后端的归一化 logprob、top-1/top-2 间距、实际选中 token，分歧是否在 EOS 之后 |
| 单步复查 | 探针输入与结果路径、是否复现、是否改变了 prefill/decode 路径 |
| 当前解释 | 已确认事实、支持的假设、尚未排除的原因，分别表述 |
| 下一步 | 一个具体可验证的实验，以及什么结果会推翻当前假设 |

本阶段不设置未经验证的“所有 token 必须一致”毕业条件，要求将差异定位到有证据、可复查的范围。20 条均一致时，只能说明该输入集合与配置下的 token 序列一致；候选接近时，记录其敏感性与尚未验证的路径；发现实现错误时，修复后保留能够捕获根因的回归测试。无法解释的差异继续标为待定位，不能通过放宽容限或改变权重直接宣告通过。
