# 开源推理项目发布与复现手册

本手册把前述实现与实验收敛为可安装、可测试、可贡献、可独立复现的开源版本。对应主计划最终交付主题与 X12，预计 20–25 小时。前置是 [项目总览](开源推理项目实施总览.md) 中必需能力已完成；尚未完成的实现先回到对应手册，不用整理文档代替功能验收。

最终作品是当前仓库中的 mini-vllm 与推理评测工具集，examples 是可检索实例材料。对外发布版本只列已实现的行为；本手册本身是实施计划，不代表现在已经完成这些功能或发布。

## 实施安排

| 工作 | 时间 | 交付 |
| --- | --- | --- |
| 功能冻结与缺口审查 | 2–3 小时 | 功能/证据矩阵、修复清单 |
| 安装包与 CPU/GPU 验证 | 4–5 小时 | 构建产物、CI、GPU 验证记录 |
| 文档、许可证与贡献入口 | 3–4 小时 | README、贡献指南、变更日志 |
| X12 生命周期与实例索引 | 5–6 小时 | 最小综合演示、实例卡、状态说明 |
| 独立目录复现 | 3–4 小时 | 新结果、复现日志、报告重建 |
| 版本说明与求职演示 | 3 小时 | 版本候选、10 分钟演示、可追溯陈述 |

## 冻结可交付范围

| 能力 | 必需证据 | 缺失时处理 |
| --- | --- | --- |
| 单请求 Qwen | 固定权重、20 条输入、oracle、停止边界 | 阻止宣称正确性基线完成 |
| 动态调度与 batch | 中途到达、真实 batch forward、不同长度、取消回收 | 回到调度手册修复 |
| 分页 KV | 真实物理存储、跨块 attention、隔离、耗尽与复用 | 逻辑 block manager 不能代替 |
| Triton 算子 | 数值/布局/回退、微基准、端到端 | 无加速可以保留实验性，正确性不可省略 |
| 服务评测 | 时间戳、失败分母、并发与到达率、监控 | 不发布无口径的吞吐对比 |
| 实验案例 | APC、profile、graph、SLO、spec、KV recovery | 报告有状态、配置与可追溯数据 |
| 可选能力 | LoRA、量化、多模态、TP/DP、上游贡献 | 以实测/仅阅读/未开展分别标注 |

把功能分为稳定、实验性、计划中，README 与 CLI 帮助保持一致。没有训练框架和集群时，首版不声称生产级服务或完整分布式推理平台。

## 形成可安装的代码与测试边界

待开发或完善的发布文件如下。沿用现有 Python 3.12 和包名 `mini-vllm`，不为发布随意重写依赖栈。

| 文件 | 必须解决的问题 |
| --- | --- |
| `pyproject.toml`、`uv.lock` | 可选 kernel/benchmark 依赖、入口、版本一致性与可复现安装 |
| `.github/workflows/ci.yml` | Python 3.12、格式/静态检查、无需模型的 CPU 测试与包构建 |
| `tests/` | 通过 marker/fixture 明确 CPU、CUDA 和 cached-model 依赖 |
| `CONTRIBUTING.md` | 开发安装、代码风格、测试分层、性能变更证据、PR 范围 |
| `LICENSE`、必要的 `NOTICE` | 自有代码许可、引用上游代码时的来源与原许可保留 |
| `CHANGELOG.md` | 当前版本实际新增行为、限制与复现入口 |

目前部分配置/oracle 测试要求本地模型，不能把 `pytest tests` 直接当成无资源 CI。先拆分纯逻辑测试与真实资源测试；资源不足产生 skip，不等于该 GPU 路径验证通过。Triton 相关导入应按可选能力处理，CPU 导入基本包不应强制初始化 CUDA。

当前可运行以下回归与构建命令；模型/GPU 需求以实际 fixture 为准，分别保存通过、跳过与失败。

```bash
cd ~/Desktop/mini-vllm
mkdir -p artifacts/release/candidate
.venv/bin/python -m pytest tests -q -p no:cacheprovider \
  > artifacts/release/candidate/tests.txt 2>&1
uv build --out-dir artifacts/release/candidate/dist
git diff --check
```

Ruff 是独立开发工具，当前不在项目依赖中。将其固定为开发工具后，对变更的 Python 文件执行 `ruff format` 与 `ruff check`。增加新 feature 的行为测试，避免只镜像实现细节；文档修改不需要增加无意义的 Python 测试。

CI 初版使用小配置和假 runner，验证状态机、映射与协议；GPU 权重验证在有资源环境执行并记录命令、模型 revision、GPU 和日志。新建无模型依赖测试应防止从顶层 fixture 意外加载 tokenizer 或下载权重。

## 从构建包验证安装

待开发验证脚本在 `artifacts/release/candidate/` 下新建虚拟环境，安装刚生成的 wheel，从仓库外的工作目录运行 import、`--help` 与无权重 smoke test。确认加载自安装包而非当前源目录；编辑安装能跑不代表 wheel 内容完整。

权重、trace、tokenizer 缓存和凭据不进入包。若 benchmark 工具仍作为仓库脚本交付，README 明确要求克隆仓库；若打包为 CLI，则检查包数据与入口声明。不能展示安装后实际不存在的 benchmark 命令。

基于当前依赖源记录 PyTorch CUDA runtime、安装方式与 wheel 适用环境。vLLM 继续使用独立环境，避免为了“一条安装命令”混合两套不兼容依赖。

## 编写面向使用者的文档

README 首屏说明项目用途、真实已支持能力和最小运行方式，随后提供安装、模型准备、正确性、服务/评测、架构、性能结论与限制入口。使用稳定功能名称，学习路线保留在 `docs/`，主入口不要求读者先完成个人学习计划。

`CONTRIBUTING.md` 给出一个新贡献者可完成的最小改动流程。性能 PR 需 baseline、hardware、model revision、workload、计时定义、正确性与重复测量；没有性能改动的 PR 不要求提交整套 GPU 基准。

选择覆盖自有代码的开源许可证，并核对引用代码的来源和原许可；上游 vLLM 示例含有版权/SPDX 声明，改写分发时保留适用声明。模型权重和第三方数据另按其许可处理，README 提供获取方式而非把权重打进仓库。

## 完成 X12 生命周期与实例索引

```bash
cd ~/Desktop/vllm
sed -n '1,180p' examples/rl/pause_resume/pause_resume_offline.py
sed -n '1,180p' examples/rl/batch_invariance/reproducibility_offline.py
rg --files examples > ../mini-vllm/artifacts/release/candidate/vllm-examples.txt
```

选择 pause/resume 或 batch invariance 的资源合适变体，明确暂停期间请求、权重和 KV 的状态，验证恢复后是否能继续完成。batch invariance 对照固定输入、模型、sampling，记录 batch 组织变化及数值路径；相同 seed 不自动保证全部配置逐位一致。

待添加 `docs/vLLM实例索引.md`，每条记录 X01–X12 对应的原入口、固定 commit、变体、命令、依赖、状态、结果、失败样本、源码与报告链接。状态使用已运行、已改造、已测量、仅阅读、未开展，不能把复制文件视为已掌握。

综合演示复用现成组件：启动固定服务 → 发起流式请求 → 回放混合负载 → 展示 metrics → 取消一个请求 → 展示已保存的短 trace → 比较 baseline/最终配置。不在演示时临时下载模型或首次 JIT；冷启动成本作为单独结果说明。

## 独立复现一个主结论

选择最有证据的一项结论，例如动态 batch 改变 makespan，或 SLO 内 goodput 的配置改善。使用新的结果目录、相同固定输入与 manifest，按公开文档执行。可以请另一位读者复现；没有第二位参与者时，在独立工作目录自查并如实记录。

| 环节 | 必须检查 |
| --- | --- |
| 源码 | 记录完整 SHA、dirty 状态，待发布改动必须在快照中 |
| 环境 | 按公开步骤创建，依赖与模型缓存来源清楚 |
| 输入 | hash、到达时序与长度匹配 |
| 执行 | 从空结果目录生成，旧 JSON/trace 不作为新输出 |
| 图表 | 从新原始数据重建表格与图，不手填结果 |
| 结论 | 数值可有离散，但方向与适用范围需重新判断 |

完整端到端性能使用无 profiler 运行，trace 用独立短窗口。若复现与报告冲突，先定位环境、温度、输入和生效配置，再修订结论；不只挑更好的一次替换报告。

## 准备公开版本

先完成本地候选版本、安装验证、报告和变更说明，按仓库既有托管流程创建可审查的变更。提交按 `feat:`、`fix:`、`docs:` 聚焦拆分。是否推送、创建 release 或上传包按实际发布任务执行；本次计划编写不执行这些远程操作。

版本说明包含：已支持行为、实验性功能、适用硬件、验证清单、性能结论及限制、安装/升级与报告链接。发布前核对候选快照没有权重、token、原始大 trace 或含个人信息的输入；实际公开材料使用可再分发的小样本。

上游 vLLM 贡献是可选结果。先挑自己复现的问题、搜索重复 issue、阅读目标仓库当前 `AGENTS.md` 与贡献要求，再准备最小修复、测试和说明；按其要求完成 review 与 AI 辅助披露，不以低价值 PR 数量作为项目验收。

## 求职展示与最终验收

10 分钟演示依次说明项目解决的问题、一次真实执行、机制与边界、性能证据、代价与复现。回答至少包括：动态到达为何影响尾延迟；分页布局与 FlashAttention 的区别；APC 的命中边界；高接受率为何可能没有投机收益；graph 启动与显存的代价；单卡结论不能直接证明多卡扩展。

简历描述只填已测数据，注明模型、硬件、负载与 SLO，并让每项陈述能指向源码、测试或报告。无显著性能提升时可以展示正确性、资源管理和诊断能力，不编造加速比。

- [ ] 必需能力实现完成，稳定/实验性/计划中状态一致。
- [ ] CPU CI、GPU 验证、完整包构建和独立安装有证据。
- [ ] README、贡献指南、许可证、变更日志齐全。
- [ ] 两个瓶颈闭环、一个无收益案例和保留负载验证可追溯。
- [ ] X01–X12 实例索引完整，资源限制与未运行项明确。
- [ ] 新结果目录能重建一个主结论及图表。
- [ ] 版本候选与演示可运行，简历每项陈述均有证据入口。
