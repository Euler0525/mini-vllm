# 基线验证与性能评测

使用 Qwen2.5-0.5B-Instruct，相同的 token 输入，对照 Hugging Face（HF）、mini_llm 与 vLLM 的 greedy 输出，并测量 vLLM 单请求离线调用。其中，输出一致性衡量的是生成 token ID 是否相同；性能数据只描述指定负载，二者不互相替代。

## 实验环境

### 模型准备

在仓库根目录执行以下命令，先安装依赖，再下载 `ModelSettings` 中固定 revision 的模型，并将 `artifacts/models/qwen2.5-0.5b` 创建为指向该 snapshot 的软链接。首次下载需要联网；已有缓存时复用缓存。权重保存在 Hugging Face 缓存中，后续运行需要保留该 snapshot。

```shell
.venv/bin/python - <<'PY'

    snapshot_download(settings.model_id, revision=settings.revision)
).resolve()
for filename in ("config.json", "model.safetensors", "tokenizer_config.json"):
    assert (snapshot_path / filename).is_file(), f"Miss model file：{filename}."

model_path = Path("artifacts/models/qwen2.5-0.5b")
model_path.parent.mkdir(parents=True, exist_ok=True)
if model_path.exists() or model_path.is_symlink():
    if model_path.resolve() != snapshot_path:
        raise FileExistsError(f"{model_path} already exist.")
else:
    model_path.symlink_to(snapshot_path, target_is_directory=True)

assert model_path.resolve() == snapshot_path
print(f"{model_path} -> {snapshot_path}")
PY
```

### HF - mini_llm

首先排查本地推理实现与 HF 基线推理结果不一致的排查过程。排查的思路是先找到第一个分歧的 token，再沿模型执行链逐层缩小范围。

使用相同的模型、参数和测试激励

|   环节    |      Hugging Face 基线      |       本地模型       |
| :-------: | :-------------------------: | :------------------: |
| Tokenizer |        Hugging Face         |     Hugging Face     |
|   权重    |      Hugging Face 加载      | 直接读取 Safetensors |
| 模型前向  |   `AutoModelForCausalLM`    | `Qwen2p5ForCausalLM` |
| Attention | 默认 SDPA，测试中使用 eager | 自定义 PyTorch eager |
| KV Cache  |     Hugging Face Cache      | 自定义连续 KV Cache  |
|   采样    |       Greedy `argmax`       |   Greedy `argmax`    |

```shell
.venv/bin/python -m mini_llm.generate
.venv/bin/python -m mini_llm.local_generate
```

HF 基线生成了 `your lunch plans`，但是本地推理生成了 `yourch lunch choices`。第 19 个 token 开始出现差异。

下一步观察本地推理第 19 个 token 时，分别对 plans 和 choices 打了多少分

在 `mini_llm/engine/generation.py/generate_tokens()` 的 `while` 循环内、调用 `sample_next_token()` 之前加入下面这段程序，

```python
    print("choices[11454]:", scores[11454].item())
    print("top5 (token_id, logit):",
          list(zip(indices.tolist(), values.tolist())))

# plans  [6649]: 19.75

# top5 (token_id, logit): [(11454, 19.875), (6649, 19.75), (2606, 19.75), (9700, 19.25), (3119, 18.75)]
```

然后查看 HF 运行到此处时对第 19 个 token 的打分，在 `mini_llm/engine/prefill_decode.py/decode()` 中的 `last_logits = outputs.logits[:, -1, :]` 后添加下面这段程序

```python

# HF plans  [6649]: 19.875
# HF choices [11454]: 19.75
# HF top5 (token_id, logit): [(6649, 19.875), (11454, 19.75), (2606, 19.75), (9700, 19.25), (3119, 18.75)]
```

这里用 `53` 定位，是因为模型已经读入 **35 个 prompt token 和 18 个共同生成 token**，接下来预测的就是发生分歧的第 19 个生成 token。这样保留了原来的逐步 decode 和 KV Cache 路径。

经过比较发现

|   候选    |   HF   |  本地  |
| :-------: | :----: | :----: |
|  `plans`  | 19.875 | 19.75  |
| `choices` | 19.75  | 19.875 |

说明两个模型确实是根据分数最高选择的下一个 token，下面要探究为什么分数会出现不一致。

---

可能的原因包括

1. KV Cache 路径问题：例如写入、读取、位置偏移存在错误；
2. 模型前向计算差异：例如 Attention 实现、RoPE、矩阵乘法精度不同；

下面将前面 53 个 token 一起作为输入给本地模型，不读取历史 KV Cache，无缓存完整前向。与刚才逐步 decode 结果对比，在 `mini_llm/engine/generation.py/generate_tokens()` 函数中刚才添加的 `if` 块中补充

```python
prefix_ids = torch.tensor(

full_ids = torch.cat([input_ids, prefix_ids], dim=1)
```

结果发现，本地的这个选择在完整前向中也会出现，不过，其它候选词的分数有变化。下面对 HF 也做无缓存实验，在 `mini_llm/generate.py` 的 `token_ids.append(output.next_token_id)` 后面添加下面测试程序


- 一次性输入 53 个 token，并且不读取历史 KV Cache：无缓存完整前向。
- 先 Prefill 35 个 token，再利用 KV Cache 逐步处理后续 18 个 token：有缓存的增量推理。

这两条路径理论上应该产生相同或数值上非常接近的 logits，但实际在 BF16 精度、不同 Attention kernel 和计算路径下，可能产生差异，尤其当候选 token 的 logits 非常接近时。

---

下面在 `mini_llm/local_generate.py/generate` 中 `load_safetensors_weights(model, model_path / "model.safetensors")` 后添加下面程序，首先验证加载后的权重逐元素一致。然后检查参数比较没有覆盖的量 RoPE 的频率常量 `inv_freq`，

```python
from transformers import AutoModelForCausalLM

hf_reference = AutoModelForCausalLM.from_pretrained(
    model_path,
    local_files_only=True,
    dtype=settings.dtype,
    attn_implementation="eager",
).eval()

expected = dict(hf_reference.named_parameters())
actual = dict(model.named_parameters())
assert actual.keys() == expected.keys(), "HF does not match the local parameter name"

mismatches = [
    name
    for name, parameter in actual.items()
    if not torch.equal(parameter.detach().cpu(), expected[name].detach().cpu())
]
print("checked parameters:", len(actual))
print("weight mismatches:", mismatches)

freqs = {}
for label, current in (("HF", hf_reference), ("mini", model)):
    name, value = next(
        (name, value)
        for name, value in current.named_buffers()
        if name.endswith(".inv_freq")
    )
    print(label, name, value.dtype)
    freqs[label] = value.detach().float().cpu()

assert freqs["HF"].shape == freqs["mini"].shape
print("inv_freq equal:", torch.equal(freqs["HF"], freqs["mini"]))
print("inv_freq max abs diff:",
      (freqs["HF"] - freqs["mini"]).abs().max().item())
del hf_reference, expected, actual
# HF model.rotary_emb.inv_freq torch.float32
# mini model.layers.0.self_attn.rotary_emb.inv_freq torch.bfloat16
# inv_freq equal: False
# inv_freq max abs diff: 0.0009441375732421875
```

此处发现一个明确的计算差异，HF 的 RoPE 频率保留为 FP32，本地转换成了 BF16，并且数值不同。RoPE 的旋转角度是位置 ✖ `inv_freq`，频率的舍入误差会影响 Q/K 的旋转，并继续传播到 Attention 和最终的 logits.

在频率检查之后添加下面程序，使用 HF 保留的原始 FP32 数值，替换所有层的 RoPE 频率，权重以及其他计算仍然使用 BF16

```python
for layer in model.model.layers:
    rope = layer.self_attn.rotary_emb
    rope.inv_freq = freqs["HF"].to(device=rope.inv_freq.device)
    assert rope.inv_freq.dtype == torch.float32
```

修改之后发现前 18 个 toke 仍然保持相同，并且第 19 个 token 修正为 `plans`，说明替换 RoPE 频率足以消除首次分歧。下面验证本地初始频率是正确的，只是模型整体转换为 BF16 时 丢失了精度。修改 `RotaryEmbedding` 类，保留 FP32 精度（而不是将舍入的 BF16 转回 FP32，无法恢复精度）

在本次样例测试中，两后端输入及 290 个参数张量一致。将本地各层 RoPE 频率替换为 HF 的 FP32 频率后，前 18 个生成 token 保持不变，第 19 个由 choices 变为与 HF 一致的 plans。该干预支持 RoPE 频率差异参与导致了本次首次分歧；并且修复后重新生成的完整序列一致，
